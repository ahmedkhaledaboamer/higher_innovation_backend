# Isolated staging: credential remediation, configuration and go/no-go

Audience: the project owner/operator. Nothing in this document has been executed against Atlas,
staging or production. Every step that touches an external system is **manual and owner-run**, and
database connectivity for staging stays **blocked in code** until you approve it (§5).

Never paste a password, connection string or secret into chat, tickets or documents. Where a value has to
be checked, use the offline commands below; they print only setting names and PASS/FAIL.

---

## 1. Credential remediation (owner, in the Atlas UI)

The Atlas database credential in the local `.env` is exposed: it was in `.env.example` (now replaced with a
placeholder) and it was shared in an IDE selection during development, so it is also present in that
development assistant's local session log and in the conversation it was sent to. **Treat it as compromised.**

### 1.1 Rotate the exposed database user's password

1. Atlas → your organization → the project that holds the cluster → **Security → Database Access**.
2. Find the database user named in the exposed connection string (look it up in your own `.env` on your
   machine; do not share it). Click **Edit** → **Edit Password** → **Autogenerate Secure Password** →
   **Update User**. Copy the new password straight into your password manager.
3. If any running deployment uses that user, it will fail to authenticate from now on. That is expected:
   it must not keep using a compromised credential. Re-issue it a new user/secret through its secret store.
4. Better than rotating in place: **create a new user** for each environment (§1.3), switch the
   environments to it, then **delete** the exposed user.

### 1.2 Review access and activity

1. **Security → Database Access**: remove users nobody can account for; check that no user has
   `atlasAdmin` or `readWriteAnyDatabase` unless it is an operator account.
2. **Security → Network Access**: remove `0.0.0.0/0` and entries nobody can explain; keep only the
   egress addresses of known environments and named administrators.
3. **Project → Activity Feed**: filter for user, network-access and cluster changes since the credential
   was first written into the project; look for changes you did not make.
4. **Database access history / Access Tracking** (cluster → *Monitoring* or *Security*, depending on the
   Atlas UI version; may require a dedicated M10+ tier): review authentications for the exposed user
   (unknown source IPs, times outside working hours).
5. **Database Auditing** (dedicated tiers only): if enabled, export the audit log for the exposed user. If
   it is not available on your tier, record that it could not be reviewed.
6. Note your findings (dates, what was checked, anything suspicious) for the release record. If anything
   suspicious shows up: keep the evidence, rotate every credential in the project, and review data changes.

### 1.3 Create a least-privilege staging database user

Preferred: a **separate Atlas project and cluster for staging**, so production data and users are not
reachable from staging at all. If staging must share a cluster, use a separate database and user:

1. **Security → Database Access → Add New Database User**.
2. Authentication: **Password** (autogenerated) — or X.509/AWS IAM if your platform supports it.
3. Privileges: **Specific Privileges** → `readWrite` on database `academy_staging` (the name must contain
   `staging`; the API refuses anything else in staging). No built-in admin roles, no `AnyDatabase` roles.
4. **Restrict Access to Specific Clusters/Federated Database Instances**: only the staging cluster.
5. Optional: **Temporary User** with an expiry date for the first staging run.
6. **Network Access**: add only the staging API's egress IP addresses.

The API also needs `listIndexes`/`createIndex` on its own database for `npm run db:indexes:prod`;
`readWrite` covers creating collections and indexes in that database.

### 1.4 Get the staging connection string without sharing it

1. Atlas → staging cluster → **Connect → Drivers** → copy the `mongodb+srv://` string.
2. Replace `<username>`/`<password>` with the staging user's values **directly in the platform secret store**
   (or a local shell variable when running the offline preflight), and append the database name
   `/academy_staging` before `?`.
3. Never paste it into chat, tickets, `.env.example`, `docs/`, or a committed file.
4. Fingerprint the **production** and **staging** cluster domains, locally (nothing is printed but hashes):

   ```bash
   npm run fingerprint:hosts
   ```

   Paste the production connection string (or just its host name) and press Ctrl+D (Windows: Ctrl+Z,
   Enter); repeat for staging. Input is read from standard input, so it does not reach shell history,
   and the output contains only hashes and label counts: never host names or credentials. Hosts are
   canonicalised exactly as the checks do (lower case, no trailing dot, decoded, numeric IP spellings
   normalised).

   For each host the script prints the exact-host hash and the hash of every parent domain.
   - `PRODUCTION_DB_HOST_SHA256` (deny-list, required in staging and production): the production
     **cluster domain**, the 3-label parent `<id>.mongodb.net` of `cluster0.<id>.mongodb.net`. A fingerprint matches a host or any parent domain of it by whole labels, so it covers
     the SRV name, every shard host (`cluster0-shard-00-00…`, `ac-…-shard-00-00…`) and private-endpoint
     hosts (`cluster0-pl-0…`) under that domain. Add the exact hash of any production host outside it (a
     custom DNS alias, a peering or private-link name in another domain). Production startup requires
     every database host to match this list.
   - `STAGING_DB_HOST_SHA256` (allow-list, required in staging): the **exact** host names in the staging
     connection string, i.e. the SRV name (`cluster0.<staging-id>.mongodb.net`) or every seed host of a
     `mongodb://` list. Domains are never accepted: a fingerprint authorises only the host it was made
     from. Hosts the cluster reports after connecting (replica set members, SRV targets) are accepted
     when they are listed exactly. The only other case is `mongodb+srv://`: hosts strictly beneath the
     parent domain of the exactly verified SRV name (`cluster0.<staging-id>.mongodb.net` → anything
     ending in `.<staging-id>.mongodb.net`). That is the MongoDB driver's own rule for SRV targets,
     made stricter: the parent must keep at least three labels, so a name such as `db.example.net`
     extends no trust. A `mongodb://` seed list never extends trust to a domain (the driver has no such
     rule for it): fingerprint every seed **and every replica set member** exactly. IP addresses and
     single-label names are refused.
   - The two lists may not share a fingerprint. Staging must be a separate Atlas project, so its
     `<id>` differs from production; if it does not, staging is refused (fail closed).
   - Fingerprints are not secrets (short host names can be guessed from their hash); they keep names
     out of configuration and logs.

### 1.5 Also check

- Editor local history (e.g. VS Code *Local History*, `.history/` folders) and backups of the developer
  machine may still contain the old `.env.example` with the credential. Rotation makes those copies useless;
  delete them if your policy requires.
- The development assistant's local session logs under the user profile (`.claude/projects/…`) contain the
  credential from the IDE selection. Rotation makes them useless; delete them if your policy requires.
- Rotate `JWT_ACCESS_SECRET` anywhere it was shared or copied (signs everyone out once).

## 2. Fix the local `.env` (owner, on your machine)

The current `.env` is rejected: `MONGODB_URI` holds two connection strings pasted together (an Atlas string
with a local string appended to its options). The API refuses to start with it.

1. Open `academy-crm-api/.env` in your editor (do not print it in a terminal).
2. Replace the whole `MONGODB_URI=` line with **one** string. For local development use the local replica
   set (no credentials), exactly as in `.env.example`:
   `MONGODB_URI=mongodb://127.0.0.1:27017/academy_crm_dev?replicaSet=rs0`
   Do **not** point local development at Atlas production.
3. Leave `DEPLOY_ENV` and `STAGING_CONNECTIVITY_APPROVED` unset locally (setting the approval flag outside
   staging is refused). Optionally set `PRODUCTION_DB_HOST_SHA256` locally too: development then refuses
   production hosts as well.
4. Verify offline (prints names only, never values):

   ```bash
   npm run config:check          # expect: ".env: OK (NODE_ENV=development)"
   ```

## 3. Staging environment variables

Template with placeholders: [`docs/staging.env.template`](staging.env.template). All values come from the
platform secret store/environment; never from files on the server, never copied from production.

| Variable | Staging value | Enforced by |
|---|---|---|
| `DEPLOY_ENV` | `staging` | required whenever `NODE_ENV=production` (`staging` or `production`); enables the isolation rules below |
| `NODE_ENV` | `production` | required with `DEPLOY_ENV=staging` |
| `MONGODB_URI` | one `mongodb+srv://` string for the **staging user**; database name with `staging` as a separate word (`academy_staging`); host names, not IP addresses; no `tlsInsecure`/`tlsAllowInvalid*` | startup, `connectDatabase()` (for the URI actually used) + preflight |
| `PRODUCTION_DB_HOST_SHA256` | fingerprint of the production cluster domain, plus any production host outside it (§1.4) | startup and `connectDatabase()` refuse a matching host or parent domain, in the URI and among the hosts the cluster reports |
| `STAGING_DB_HOST_SHA256` | exact fingerprints of the staging host names (§1.4) | every URI host must be listed exactly; reported hosts must be listed exactly, or (`mongodb+srv` only) lie under the verified SRV name's parent domain |
| `STAGING_CONNECTIVITY_APPROVED` | `false` until you approve (§5); refused outside `DEPLOY_ENV=staging` | `connectDatabase()` refuses while false |
| `JWT_ACCESS_SECRET` | new random 48+ characters, staging only | startup (≥ 32) + preflight |
| `CORS_ORIGINS` | staging frontend origin(s), https | preflight |
| `FRONTEND_URL` | staging frontend URL, https (used in email links) | preflight |
| `COOKIE_SECURE` | `true` | startup (production) |
| `COOKIE_SAMESITE` | `strict` (same site) or `none` (cross-site; needs `COOKIE_SECURE=true`) | startup |
| `TRUST_PROXY` | number of proxies in front of the API (usually `1`) | preflight |
| `MAIL_TRANSPORT`, `SMTP_*`, `MAIL_FROM` | `smtp` + **sandbox** SMTP credentials | startup (production) + manual |
| `BCRYPT_ROUNDS` | `12` (≥ 10) | startup (production) |
| `API_DOCS_ENABLED` | `false` unless staging Swagger is wanted | preflight warns |
| `LOG_LEVEL` | `info` | — |
| Rate limits / TTLs | defaults (`RATE_LIMIT_MAX=300`, `AUTH_RATE_LIMIT_MAX=10` per 15 min; access 900 s; refresh 7 d; reset 30 min; invite 72 h) | — |

Frontend build for staging: `VITE_API_URL=https://<staging-api>/api/v1` (or `/api/v1` behind a same-origin
reverse proxy). No secrets in any `VITE_*` value.

## 4. Preflight: proving staging cannot target production

Run on the staging host **before** approving connectivity (offline; prints names and PASS/FAIL only):

```bash
npm run build
npm run preflight:staging            # checks the real staging environment variables
```

It must print `Automatic checks passed.` Automatic checks:

| Check | Proves |
|---|---|
| `config.valid` | the whole configuration parses, including the staging isolation rules |
| `deploy.identity`, `deploy.mode` | `DEPLOY_ENV=staging`, `NODE_ENV=production` |
| `connectivity.blocked` | approval flag still false while preflighting |
| `db.single-uri` | exactly one connection string |
| `db.readable` | host list and database name can be read (otherwise fail closed) |
| `db.name` | database name contains `staging` as a separate word |
| `db.driver-parse` | the MongoDB driver's own parser reads the same hosts and database as the checks |
| `db.denylist`, `db.not-production` | production fingerprints configured; no staging host, nor any parent domain of it, matches them |
| `db.allowlist`, `db.staging-host` | staging fingerprints configured; every connection-string host is exactly declared |
| `db.hostnames`, `db.tls-validation` | host names (IP addresses cannot be fingerprint-checked); TLS validation not disabled |
| `db.remote`, `db.tls` | a managed, TLS-protected database (not localhost) |
| `http.frontend-https`, `http.cors-https` | browser-facing URLs are HTTPS |
| `cookie.secure`, `proxy.trust` | secure cookies; correct client IPs for rate limiting |
| `secret.jwt` | a real JWT secret, not a placeholder |
| `mail.smtp` | SMTP transport configured (sandbox confirmed manually) |
| `docs.off` | Swagger off unless intended |

Manual items printed with it (confirm and record): fingerprints cover the production cluster domain and any production host outside it, and the staging list covers only staging; staging is a separate Atlas project whose user cannot authenticate to production; sandbox SMTP host; staging DB user privileges; Atlas
network access list; snapshot taken and restore rehearsed; secrets from the secret store; frontend built
against the staging API.

The same isolation rules run again at API startup. `connectDatabase()` (server, `db:indexes:prod`,
`db:seed:prod`, test helpers) is the only code that opens an application connection (enforced by a test).
For every call, in order:

1. Refuses while `STAGING_CONNECTIVITY_APPROVED` is not `true`; re-checks identity and target rules for the
   URI actually given; requires the MongoDB driver's own parser to read the same hosts and database.
2. Verifies on a separate **probe** connection with no models, no queued commands and no automatic
   operations: it sends only `hello`, checks every host the cluster reports and every server the driver
   reached (the SRV targets), then closes.
3. Opens the application connection with Mongoose's automatic operations held back (no collection or
   index creation, no replay of queued queries; a query issued early fails instead of being queued).
4. Verifies that connection's hosts again (DNS may have changed since step 2).
5. Only then creates collections and (outside production) indexes, enables buffering, and watches the
   topology: when the driver announces a server it did not have before (replica set reconfiguration,
   SRV polling of a sharded cluster) and that server is not allowed, the connection starts closing.
   This is best effort, **not a guarantee**: the driver does not use a new server before its first
   monitoring check, but closing is asynchronous (the driver first ends cursors and sessions, which can
   send commands), so an operation can still be dispatched while the close is in progress. The API then
   stays up without a database (readiness reports 503) rather than exiting.

Any refusal disconnects, and nothing from the application has reached the server; the TLS and
authentication handshake of steps 2–3 is the only traffic (see "Limits" below). Connection errors are
reported without credentials or nested causes.

**Limits.** Host checks see names, not ownership. A DNS alias that points a staging name at a production
mongos (sharded clusters report no member names) cannot be detected by name; the backstop is that the
staging database user exists only in the staging Atlas project and cannot authenticate to production,
plus the network access list. Verification needs the handshake, so the staging credentials are offered to
whatever answers on the verified name. Host names are not re-checked when the driver reconnects or
opens new pooled connections, so a DNS change for an already-verified name is not detected either.

## 5. Connectivity gate

External connectivity tests stay blocked until **both**:

1. you confirm, in writing, that the staging environment is separate (its own Atlas project/cluster or
   database and user, its own secrets, sandbox SMTP), and
2. `npm run preflight:staging` passes on that environment and the manual items are confirmed.

Only then set `STAGING_CONNECTIVITY_APPROVED=true` in the staging environment, and proceed with §6.

## 6. Staging checks after approval (runbook summary)

Details: [RELEASE-READINESS.md](RELEASE-READINESS.md) §6.

- **Replica set & version**: API boot log shows "Connected to MongoDB" (it refuses standalone servers and
  MongoDB < 5.0).
- **Backup/restore**: enable continuous backup or snapshots; take a snapshot; restore it into a scratch
  database and record the duration.
- **Indexes**: `npm run db:indexes:prod` (15 collections incl. `contactlocks`), then `npm run db:seed:prod`
  once. Rollback: the new collection/indexes can be dropped; the previous API ignores them.
- **HTTPS/proxy**: HTTP redirects to HTTPS; HSTS; `X-Forwarded-For` forwarded; two client IPs get separate
  `RateLimit-Remaining` counters; logs show client IPs.
- **CORS**: unlisted origin → 403; staging frontend works with credentials.
- **Cookies**: `crm_refresh` is `HttpOnly; Secure; SameSite=Strict` (or `None` cross-site), `Path=/api/v1/auth`.
- **Rate limits**: 11 wrong passwords for one account within 15 minutes → 429.
- **Sandbox SMTP**: invitation and reset emails arrive in the sandbox, links point to the staging frontend,
  links work once. (Locally, `MAIL_TRANSPORT=outbox` writes to `.outbox/` instead.)
- **Smoke tests**: authentication, lead conversion, duplicate contacts, enrollment, trainer isolation,
  campaign attribution, reporting, role matrix (RELEASE-READINESS.md §5).

## 7. Staging go/no-go checklist

**No-go until every item is checked.** Items marked (code) are enforced automatically once configured.

Credentials and configuration
- [ ] Exposed Atlas credential rotated or the user deleted (§1.1); access/activity reviewed and recorded (§1.2)
- [ ] Local `.env` fixed; `npm run config:check` → OK (§2)
- [ ] Staging Atlas project/cluster or database separate from production; least-privilege staging user (§1.3)
- [ ] Staging secrets only in the platform secret store; new `JWT_ACCESS_SECRET`; sandbox SMTP credentials
- [ ] `PRODUCTION_DB_HOST_SHA256` contains the production cluster domain fingerprint (and any production host outside it), in staging and production (code)
- [ ] `STAGING_DB_HOST_SHA256` contains only the exact staging connection-string host fingerprints (code)
- [ ] Staging cluster is in a separate Atlas project (different `<id>.mongodb.net` domain)

Preflight and gate
- [ ] `npm run preflight:staging` → "Automatic checks passed." on the staging host
- [ ] Manual preflight items confirmed and recorded
- [ ] Owner's written approval of staging connectivity; then `STAGING_CONNECTIVITY_APPROVED=true` (code gate)

Platform
- [ ] HTTPS end to end; reverse proxy forwards client IP; `TRUST_PROXY` set
- [ ] Snapshot taken; restore rehearsed (duration recorded)
- [ ] `db:indexes:prod` and `db:seed:prod` run against **staging** only

Verification on staging (not before)
- [ ] Health/readiness green; startup checks passed (replica set, version ≥ 5.0)
- [ ] CORS, cookie, rate-limit and SMTP sandbox checks (§6)
- [ ] All smoke tests pass with the seven role accounts
- [ ] Logs free of tokens, cookies, passwords and connection strings

Release decision
- [ ] Open findings resolved or explicitly accepted (RELEASE-READINESS.md §1)
- [ ] Staging sign-off recorded. Production is a separate, approved step.
